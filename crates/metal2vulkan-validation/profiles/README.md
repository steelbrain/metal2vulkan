# Committed device profiles

Khronos profiles-schema (0.8) JSON, one profile per file (`VP_M2V_<file stem>`), each with a
top-level `provenance` object. Generated by `scripts/regen-device-profiles/`; do not hand edit
(the lint rejects non-canonical files). The translator parses them into a `DeviceDescription`;
validation uses them for per-profile checks.

**Venue profiles.** The profile a venue names
(`crates/metal2vulkan-validation/cutover/c3-venues.json`), and the capture of each further device a venue allows, is a
`vulkaninfo` capture of that device with its `corpus-vulkan --capture-formats` supplement:
`moltenvk-m3`, `gate-lavapipe`,
`gate-lavapipe-x86_64`, `amd-780m-radv`, `intel-irisxe-rplp-anv` (with `intel-uhd770-rpls-anv`,
the venue's RPL-S device), `nvidia-rtx5080-laptop`. The venue list
refuses a file that is not such a capture, whose device identity is not the one the venue
declares for it, or that derives another translation key than the venue's profile. The gpuinfo
files above are census profiles of devices in the wild; no venue names them. Nor does it
name `amd-780m-hawkpoint-radv`, the Radeon 780M of Hawk Point: the GPU of `amd-780m-radv` under
another `deviceID` (0x1900), whose capture under the same RADV build differs from `amd-780m-radv`'s
only there, so it takes the 780M's measured driver facts and derives the same translation key.

Reading notes for consumers of these files:

- A capability the source does not report is absent. Treat absence as "not supported", never as
  a default.
- Blocks named `m2v_vulkan12_required_formats*` are not from the profile's source: they are the
  Vulkan 1.2 specification's Required Format Support entries that a requirements profile stating
  no formats implies, generated from the pinned specification text (`provenance.required_formats`
  names it and lists the conditional requirements no single profile can state).
- In the derived profiles, a member the base profile states at a value the Vulkan 1.2
  specification contradicts takes the specification's value instead, each named in
  `provenance.spec_corrections`: `supportedDepthResolveModes` and `supportedStencilResolveModes`,
  which the base states empty and the specification requires to include
  `VK_RESOLVE_MODE_SAMPLE_ZERO_BIT`, and `maxDrawIndexedIndexValue`, which the base states as
  `2^24` and the Required Limits table as `2^24 - 1`.
- The block `m2v_unrequired_properties` of the derived profiles is not from the base profile
  either: it states the weakest value the specification permits for each property the product
  reads, and `VK_LAYER_KHRONOS_profiles` sets, that the base leaves without a requirement. That
  is the value a reader takes for the absent member; stated, the layer (which keeps the device's
  own value for a member a profile omits) reports it too.
- The block `m2v_layer_presentation` of `lunarg-desktop-baseline-2023` and `roadmap-2022` is not
  from the profile's source either: it states each feature the profile's core version requires
  that the profile omits, and each member the product reads of the core property structures of
  its version and of the property structures of the extensions it lists that it omits, at the
  value the product's reader takes for the absent member (`provenance.layer_presentation` lists
  them). The product's reading does not change; the
  profiles layer, which reports the device's own value for an omitted member and an omitted
  feature as absent, then reports the profile as the product reads it. Validation refuses to
  restrict a device to a requirements document (`khronos`) without it.
- A file states what its source reports, not what the driver honors. `moltenvk-m3` states
  `robustBufferAccess` as MoltenVK reports it, but MoltenVK adds no bounds check for it: on the
  captured device out-of-bounds storage and uniform buffer accesses, buffer atomics, and vertex
  fetches read and wrote the next buffer's memory, while texel buffers were contained. Validation records it as a driver limitation (`HostClass::robust_buffers_uncontained`).
- A file states no deviation from the specifications: where a driver's answer to what they leave
  open is Metal's (MoltenVK's lockstep, float functions, canonical NaN, sampler and cube-gradient
  route on Apple's GPUs), the product takes it from the release-keyed table of what each driver
  release is measured with (`crates/metal2vulkan/src/device/driver_facts.rs`),
  keyed on the file's `driverID`, `vendorID` and `driverVersion`. The product refuses a file that
  holds the former top-level `m2v_deviations` object.
- The top-level object `m2v_color_attachment_sample_counts` of a venue profile, keyed by profile
  name, states each color attachment format's own sample counts (`VkSampleCountFlagBits` names):
  the `sampleCounts` of a 2D, optimal-tiling image of the format with `COLOR_ATTACHMENT` usage,
  which no profiles-schema structure holds (`VkImageFormatProperties`). The venue capture's
  `corpus-vulkan --capture-formats` supplement measures them. A file without it
  states no format's own counts, only the device-wide `framebuffer*SampleCounts`.
- `provenance.unmapped` lists report fields the converter could not represent (pointer members,
  flag bits outside the registry, extensions outside the registry; for a `vulkaninfo` capture, a
  driver's unpublished extension and a pointer member vulkaninfo wrote as `NULL`). They are
  dropped, not guessed.
- No file carries host identity: the device-property members that identify the
  reporting host or driver build (every UUID and LUID, the PCI address, the DRM node numbers) are
  withheld, and `provenance.withheld` names the ones the source reported. Their absence says
  nothing about what the device supports.
- gpuinfo-derived files carry both the core `VkPhysicalDeviceVulkan1x*` structs and the
  extension structs the report lists, as reported; they are not reconciled.
- Integers keep the report's full width (`maxTimelineSemaphoreValueDifference` can be
  `2^64 - 1`), so parsers need `u64`.
